# ViBilet 技術設計書（公開版）

> 本書は内部技術設計書を基に、アーキテクチャと設計判断を中心に再構成した資料です。記載内容には実装済みの仕組みと設計・拡張予定が含まれます。具体的なゲームバランス値、内部判定条件、未確定の実装詳細は省略しています。実装状況の最終的な確認にはソースコードおよびテストを参照してください。

## 1. 文書概要・技術設計方針

## 1.1 目的
ViBiletは、現実時間とともに状態が変化するデジタル生命体「LIFE」を育成するモバイルアプリケーションです。本書は、ゲームシステムの要求をFlutter/Dart上で実現するための技術的な構成と責務分担を説明します。

設計上の重点は以下のとおりです。

- UIとゲームロジックを分離し、表示変更が生命状態の更新処理に影響しにくい構造にする。
- 時刻取得を抽象化し、アプリ非起動中の時間経過と再現可能なテストに対応する。
- 状態の保存・復元をRepositoryに集約し、永続化方式への依存を局所化する。
- 保存すべき状態と計算可能な派生値を区別し、データの不整合を抑える。
- 成長により外見が変化しても、同じ個体の状態を維持する。
- キャラクターの追加に際して、共通ロジックの変更を最小限にする。

## 2. 技術スタックとアーキテクチャ

- **フレームワーク：** Flutter
- **言語：** Dart
- **対象：** モバイル端末
- **データ管理：** ローカル保存を基本とする構成

アプリケーションは、概念上、以下の責務に分割します。

```text
ユーザー操作・画面表示（UI）
            ↓
       Controller
            ↓
   Game Logic / Services
            ↓
      State / Models
            ↓
        Repository
            ↓
      Local Storage
```

この図は主要な依存関係を簡略化したものであり、すべてのクラスが必ず直列に呼び出されることを意味しません。ControllerはUIからの操作を受け付け、Serviceはゲームルールや状態更新を担当します。Repositoryは永続化を担当し、Widgetが保存処理やゲームルールを直接実装することを避けます。

## 3. データモデルと状態管理

### 3.1 LIFEの状態

`LifeState`は、現在の個体を復元し、生命活動を継続するために必要な状態を保持する中心的なモデルです。主な情報群は次のとおりです。

| 情報群 | 主な役割 |
|---|---|
| 個体識別 | 個体ID、名前、現在のキャラクター識別子 |
| 時間情報 | 誕生時刻、最終更新時刻 |
| 生命状態 | 空腹、関係性、世話の履歴、寿命、生命活動状態 |
| 成長状態 | 成長段階、進化系統、適用待ちのPATCH |
| 環境状態 | JUNK DATA、DATA ERRORなど |
| 所持・継承情報 | デジペレット、世代に関連する情報 |

具体的なフィールド名やデータ型は実装に従います。

### 3.2 個体識別と形態識別

個体を識別する情報と、現在表示するキャラクター形態を識別する情報は別の役割を持ちます。

```text
同一のLIFE（個体識別子は維持）
  PIX
   ↓ 成長PATCH
  BLAZE / FLOW / BLOOM 系統の成長形態
   ↓ 成熟
  対応する成熟形態
```

成長は新しい個体の生成ではなく、既存個体の形態・プロフィールの変化として扱います。名前、誕生時刻、関係性など、継続すべき状態を維持することが重要です。

### 3.3 派生値

`Age`、`DAY`、`SATIETY`、表示用の`CONDITION`などは、保存済み状態から導出できる場合、独立した永続データとして重複保持しない方針です。これにより、複数の保存値が食い違うリスクを低減します。

## 4. 時間管理とオフライン進行

### 4.1 時刻取得の抽象化

時間依存ロジックは、システム時計を直接参照するのではなく、`TimeService`のような抽象化された時刻取得手段を利用する設計です。

```dart
abstract class TimeService {
  DateTime now();
}
```

通常実行時には実時刻を返し、テスト時には任意の時刻を与えられる構造にすることで、長期間の経過や境界時刻の検証を容易にします。

### 4.2 非起動中の経過時間

ViBiletでは、アプリを閉じている間もLIFEの時間が進行します。常時バックグラウンドでゲームループを実行することを前提とせず、前回更新時刻と現在時刻の差から経過時間を求め、必要な状態更新を行う方式を基本とします。

```text
保存済みの最終更新時刻
          ↓
     現在時刻を取得
          ↓
       経過時間
          ↓
  時間依存の状態を更新
          ↓
      状態を保存
```

時間経過による更新対象には、空腹、関係性、環境状態、成長イベント、寿命などが含まれます。更新の順序や境界条件はゲームロジック側で管理します。

### 4.3 誕生時刻を基準とする表示

`Age`とHOME画面の`DAY`は、同じ誕生時刻を基準に算出します。端末の暦日が切り替わったことだけを成長の判定条件とはせず、実際の経過時間を基準にします。成長後も誕生時刻を変更しないため、LIFEの経過時間は連続します。

## 5. ゲームロジックとシミュレーション

ゲームルールは責務ごとにServiceへ分離する方針です。以下は主要な責務の例です。

| 領域 | 主な責務 |
|---|---|
| Hunger / Feeding | 空腹状態の更新、給餌による変化 |
| Bond | LIFEとユーザーの現在の関係性 |
| Care | 生涯を通じた世話の評価 |
| JUNK DATA | 不要データの蓄積、清掃、異常状態との連携 |
| Behavior | LIFEの活動状態と行動の選択 |
| LifeSimulation | 経過時間に応じた複数の状態更新の調整 |

`LifeSimulation`は、各領域のルールを単一の巨大なWidgetに集約せず、時間経過に伴う処理を調整する役割を担います。特定の状態が優先される場合や、複数の更新が競合する場合も、ゲームロジック側で一貫した結果を得られるようにします。

画面上の状態表示は、原則としてモデルやServiceの結果から導出します。たとえば`CONDITION`は、独立した生命力パラメータを増やすのではなく、既存の生命状態を利用した表示情報として扱います。

## 6. 成長・ライフサイクル管理

### 6.1 成長PATCH

成長イベントは、経過時間、LIFEの状態、適用待ちのPATCH情報などを基に管理します。成長系統には`BLAZE`、`FLOW`、`BLOOM`を使用します。

```text
PIX
 ↓
成長イベントの判定
 ↓
PATCHの選択・適用
 ↓
選択系統の成長形態
 ↓
成熟イベントの判定
 ↓
同系統の成熟形態
```

PATCHの表示や演出はUIが担当し、適用可能性や状態変更はゲームロジックが担当します。アプリ終了後も必要なイベントを復元できるよう、適用待ち状態を永続化の対象とします。

### 6.2 生命活動の終了

LIFEには有限の寿命があり、生命維持に関する条件によって終了する場合もあります。終了の判定はライフサイクル管理の責務とし、画面遷移や終了演出とは分離します。

### 6.3 MEMORY DATAと世代継承

世代間の継承情報は、現在のLIFEの状態とは区別して管理する方針です。前世代の記録を次世代に利用する場合も、個体の識別子や誕生時刻を引き継いで同一個体として扱うのではなく、新しいLIFEとして開始します。生成・継承の詳細条件は公開版では省略します。

## 7. データ永続化と復元

保存・読込処理は`Repository`に集約し、ゲームロジックが特定の保存方式へ過度に依存しない構造を目指します。

主な永続化対象は、個体の識別情報、生命状態、誕生・更新時刻、成長・PATCH状態、環境状態、所持情報、世代に関する記録です。一方、計算で再現できる表示値や一時的なアニメーション状態は、必要性を検討したうえで保存対象から除外します。

起動・復帰時には、概念上、以下の流れで状態を整合させます。

```text
アプリ起動・復帰
      ↓
保存状態の読込
      ↓
経過時間に基づく状態更新
      ↓
必要な状態の保存
      ↓
生命活動・成長イベント等の確認
      ↓
適切な画面を表示
```

未処理のPATCHや生命活動終了など、通常のHOME表示より優先すべき状態を考慮します。重複更新やイベントの再適用を避けるため、状態更新と保存の境界を明確にすることを重視します。

## 8. キャラクター表示とアセット管理

キャラクターの共通表示処理と、個別の形態・モーション定義を分離します。`CharacterProfile`のようなプロフィール定義を通じて、種族情報、活動リズム、性格、説明文、表示に必要な設定を参照する構成です。

キャラクター表示側は、現在の識別子と状態に応じたアセットを選択し、待機・移動・食事・ふれあい・睡眠などのモーションを再生します。アニメーションのフレームや再生方法を共通化することで、形態ごとに同じ制御処理を重複実装することを抑えます。

ドット絵の描画では、意図しない補間によって輪郭がぼやけないようにすることも重要です。また、JUNK DATAによる表示破損は、原則として表示レイヤーやアセット選択で表現し、保存済みのキャラクター情報自体を破壊しません。

キャラクター追加時の互換性やアセット不足時の代替表示についても、拡張性と安定性の観点から検討します。

## 9. UIとゲームロジックの責務分離

一時的な視覚効果と、永続的な生命状態を区別します。

| UI側で扱う情報 | ゲームロジック側で扱う情報 |
|---|---|
| 表示位置・向き | 個体識別・生命活動状態 |
| アニメーションフレーム | Hunger・Bond・Care |
| タップ時の演出 | Lifetime・成長段階 |
| ノイズ・粒子・表示破損 | JUNK DATA・DATA ERROR |
| 画面遷移中の一時状態 | PATCH適用待ち状態 |

たとえば、LIFEがタップに反応して近づく演出と、TOUCH操作による関係性の変化は別の責務です。同様に、画面上のノイズを消す処理と、永続化されたJUNK DATAの値を変更する処理も分離します。

これにより、見た目の変更やアニメーション追加がゲームルールへ与える影響を抑え、テスト範囲を明確にできます。

## 10. テスト容易性と品質設計

ViBiletでは、時間経過と状態遷移を中心に、ロジックを自動テスト可能な単位へ分離することを重視します。

主な検証観点は以下のとおりです。

- **時間境界：** 任意の時刻を注入し、日数の切替や長期間の経過を検証する。
- **状態更新：** 給餌、関係性、世話、環境状態などの更新結果を検証する。
- **成長イベント：** イベント発生、PATCH適用、適用待ち状態の復元を検証する。
- **ライフサイクル：** 自然終了、生命維持失敗、次世代開始の状態遷移を検証する。
- **永続化：** 再起動後の状態復元、重複更新の防止、派生値との整合性を検証する。
- **表示：** アセット選択、JUNK DATAの視覚効果、入力操作への影響を検証する。

Service単体テスト、Widgetテスト、複数機能をまたぐ統合テストを、対象の責務に応じて使い分けます。実機固有の挙動、通知、描画品質、アクセシビリティなどは、別途テスト計画に基づいて確認します。

## 設計上のまとめ

ViBiletの技術設計は、**現実時間に沿って変化する一つのLIFEを、アプリの起動・終了や形態変化をまたいで一貫して扱うこと**を中心に構成しています。

時間処理の抽象化、状態と派生値の区別、責務ごとのService分離、Repositoryによる永続化、キャラクター表示の共通化を組み合わせることで、機能追加と検証を継続しやすい構造を目指します。
