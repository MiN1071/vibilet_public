# ViBilet — テスト計画書（公開版）

> 本書は、ViBilet初期版の品質保証方針、テスト戦略、対象範囲、検証観点および完了基準を定義する公開用のテスト計画書です。個別テストケース、実施結果、合否実績および品質評価結果は、別途作成する「テスト仕様書兼成績書」で管理します。開発中の機能については、実装状況に応じてテスト対象・実施時期を見直します。

## 1. 文書概要

### 1.1 目的

デジタル生命体育成アプリ **ViBilet** の初期リリースに向け、品質上のリスクを明確化し、それらを検証するためのテスト方針、テストレベル、役割分担、実施条件および完了基準を定める。

ViBiletでは、LIFEがアプリの非起動中も実時間に従って変化し、成長、生命活動の終了、世代交代へと進む。そのため、画面が正しく表示されることに加え、**時間経過・状態遷移・永続化の整合性**を重点的に検証する。

### 1.2 関連文書

- `01_REQUIREMENTS.md`：要件定義書
- `03_GAME_SYSTEM.md`：ゲームシステム仕様書
- `04_UI_FLOW.md`：UI・画面仕様書
- `05_TECHNICAL.md`：技術設計書

関連文書の公開状況およびファイル名は、公開リポジトリの構成に従う。個別テストケース、実施結果および品質評価は、別途作成する「テスト仕様書兼成績書」を参照する。

### 1.3 本書の位置づけ

本書は**何を、なぜ、どのように検証するか**を定める計画文書であり、テスト実施済みであることや合格を表明する文書ではない。内部管理用の詳細なテスト項目一覧や仕様差異管理記録とは役割を分ける。

## 2. 品質保証の基本方針

### 2.1 品質目標

- **状態の正確性**：操作・時間経過に対して、ゲーム状態が仕様どおりに更新される。
- **時間的一貫性**：非起動期間を含め、同じ時刻条件から一貫した結果が得られる。
- **データの継続性**：再起動・復帰・成長後も、同一個体の情報と記録が適切に保持される。
- **遷移の安全性**：成長、生命活動終了、世代交代などの重要イベントが重複・欠落しない。
- **操作性と可読性**：視覚演出が主要操作を妨げず、さまざまな端末で利用できる。
- **変更への耐性**：キャラクターや演出を追加しても、共通機能と既存データが損なわれない。

### 2.2 テスト設計思想

テストは実装されたメソッドの数ではなく、**利用者に影響する失敗の可能性と影響度**を基準に設計する。特に、取り消しにくい状態変更（生命活動終了・成長確定・世代継承）や保存データの破損は優先的に検証する。

各機能では、正常系に加えて境界値、異常系、再実行、復帰・再起動、複数イベントの競合を検討する。UIの表示検証とゲーム状態の検証を分け、問題発生時に原因を特定しやすくする。

### 2.3 テスト可能性を支える設計

時刻取得を`TimeService`等で抽象化し、テストでは任意の時刻を与えられるようにする。ゲームルールをServiceへ、保存・読込をRepositoryへ分離することで、実機操作に依存せず状態遷移を再現可能にする。テスト用の状態や依存先は、本番用の保存データと混在させない。

## 3. テスト戦略とリスク分析

### 3.1 リスクに基づく優先順位

| 重点リスク | 想定される不具合 | 主な検証方法 | 優先度 |
|---|---|---|---|
| 時間経過の不整合 | 長期未起動後の状態更新漏れ・二重更新 | 単体・時間シミュレーション・復帰試験 | 高 |
| 重要イベントの誤処理 | 成長PATCHの重複適用、終了イベントの欠落 | 状態遷移・統合・再起動試験 | 高 |
| 永続化の不整合 | LIFE情報・MEMORY DATAの消失や不正復元 | Repository・統合・更新受入試験 | 高 |
| 生命維持ロジックの誤判定 | 境界条件での誤終了・終了漏れ | 境界値・経過時間試験 | 高 |
| 表示と内部状態の不一致 | JUNK演出が保存値を破損、表示更新漏れ | Service・Widget・統合試験 | 中〜高 |
| キャラクター追加による退行 | 共通操作の停止、Asset不足時の例外 | 拡張性・互換性・回帰試験 | 中〜高 |
| 端末依存の不具合 | 通知不達、画面欠け、操作困難 | 実機・OS通知・アクセシビリティ試験 | 中〜高 |

優先度は初期計画時の相対評価であり、実装変更や不具合の発見に応じて見直す。

### 3.2 テストレベルと役割

| テストレベル | 主な目的 | 実施手段 |
|---|---|---|
| 単体テスト | モデル・サービス・保存処理の規則と境界を検証 | Dart / Flutterの自動テスト |
| Widget・画面テスト | 表示、入力、画面分岐、UIと状態の接続を検証 | Flutter Widgetテスト |
| 統合・時間シミュレーション | 複数サービスの処理順序、復帰、ライフサイクルを検証 | 制御可能な時刻・テスト用Repository |
| リリース前テスト | OS・端末・配布物に依存する品質を検証 | 実機試験、受入試験、必要に応じた手動確認 |

### 3.3 回帰テスト方針

ゲームルール、保存形式、画面遷移、キャラクター定義などの変更時には、変更箇所だけでなく、影響を受ける共通機能を再検証する。自動テストは継続実行可能な回帰確認の基盤とし、実機依存の観点はリリース候補ごとに確認する。

## 4. テスト対象・範囲

### 4.1 対象機能

- LIFEの誕生・命名・状態管理・復元
- Hunger、Bond、Care、Lifetime等のゲームロジック
- 自律行動、行動優先順位、時間依存の状態更新
- JUNK DATA、DATA ERRORおよび関連する視覚演出・清掃操作
- 成長PATCH、成長系統（`BLAZE / FLOW / BLOOM`）、成長段階の遷移
- 生命活動の終了、MEMORY DATA、次世代への引き継ぎ
- 画面遷移、共通操作、キャラクター表示・アニメーション
- 通知の判定・重複防止・OS上での動作
- データ保存・読込、アプリ再起動・復帰、配布ビルド

### 4.2 対象範囲の管理

未実装または仕様確定前の機能は、**計画対象**と**実施可能な対象**を区別する。仕様変更があった場合は、要件・設計・テスト観点の対応関係を確認してからテスト仕様を更新する。

### 4.3 対象外・制約

本書は個別ケースの手順・期待結果・実績を記載しない。サーバー側の機能やオンラインサービスなど、初期リリースの対象外となる機能は、実装・採用が決まった段階で計画に追加する。iOS実機試験など、実施環境が確保されていない項目は未実施として明示し、実施済みと扱わない。

## 5. 単体テスト方針

Service、Model、Controller、Repositoryを対象に、入力条件と期待する状態変化を検証する。

重点観点は次のとおり。

- **境界値**：最小値・最大値・しきい値直前と到達時。
- **時間条件**：日付跨ぎ、一定時間経過、時刻が逆行した場合などの扱い。
- **状態遷移**：正常な変更、禁止された変更、終了後の操作抑止。
- **冪等性**：同一イベントの再評価によって、配布・成長・記録生成が二重実行されないこと。
- **保存と復元**：モデルのシリアライズ、必須項目、既存データとの整合。
- **例外・不足データ**：未登録キャラクターや不足Assetなどに対する安全な代替処理。

テストでは外部時刻や保存先を制御し、実行順序によって結果が変わらない構成を目指す。

## 6. Widget・画面テスト方針

Flutter Widgetテストでは、画面表示、入力イベント、画面遷移、ゲーム状態の反映を確認する。

主な観点は、誕生・命名・HOME・LIFE DATA・PATCH・生命活動終了・MEMORY DATAの表示と遷移、FOOD・TOUCH等の操作、起動時の状態に応じた画面分岐である。

JUNK DATAなどの視覚演出については、表示段階の切替、操作領域への干渉、表示用の文字化けが保存データを変更しないことを確認する。アニメーションの滑らかさ、実際の画質、端末ごとの操作感はWidgetテストだけでは保証できないため、実機確認を併用する。

---

## 7. 統合・時間シミュレーションテスト方針

### 7.1 目的

複数Serviceの連携により、長時間の経過後もLIFEの状態とイベント順序が矛盾しないことを確認する。実時間で待機せず、制御可能な時刻を用いて経過時間を再現する。

### 7.2 重点シナリオ

- 非起動期間をまたぐHunger・Bond・Care・JUNK DATA等の更新。
- 成長イベントの発生、PATCH待機、再起動後の復元、適用後の状態維持。
- 成長・生命活動終了など、同時期に発生し得るイベントの優先順位。
- 終了後に不要な状態更新や通知が継続しないこと。
- MEMORY DATA生成から次世代開始までの記録保持と個体IDの独立性。
- 同じ保存状態を再読込した際に、処理済みイベントが重複しないこと。

### 7.3 整合性の検証

画面の表示結果だけでなく、更新後の状態、永続化された値、再読込後の値を比較する。重要な状態遷移については、途中でアプリを終了・再起動する条件も含める。

## 8. 拡張性・互換性・回帰テスト方針

新しいキャラクターや成長形態を追加した場合でも、共通操作や既存の保存データが正常に機能することを検証する。

- キャラクター登録と`individualId`の独立性。
- キャラクターごとに異なるモーション構成の受け入れ。
- 共通操作の継続利用とアニメーション切替。
- 未登録IDや不足Assetに対するフォールバック。
- 成長後も同一個体の名前・誕生時刻・関係情報が保持されること。
- 既存セーブデータ、MEMORY DATA、成長経路との互換性。

拡張機能の受け入れ条件は、追加対象ごとにテスト仕様書兼成績書へ具体化する。

## 10. テスト実施管理・品質ゲート・完了基準

### 10.1 実施前条件

- テスト対象の要件・設計・期待動作が確認できること。
- 対象ブランチ・コミット・Flutterバージョンを特定できること。
- テストデータ、時刻条件、保存先、端末・OS等の前提条件が記録されること。
- 未確定仕様や既知の差異が識別され、判定に必要な前提が整理されていること。

### 10.2 結果・証跡の管理

個別ケースには、識別子、対象要件、前提条件、手順、期待結果、実際の結果、PASS / FAIL / 未実施 / 保留の状態、実施日、実施環境、証跡を記録する。これらは別文書の「テスト仕様書兼成績書」で管理する。

**テストコードの存在は、テストの実行・合格を意味しない。** 実績値は対象コミットの実行ログ等で確認し、計画値と区別する。

### 10.3 不具合・仕様差異の管理

期待結果と実際の結果が一致しない場合、実装不具合か仕様差異かを切り分ける。仕様が曖昧な場合は、関係する要件・設計を確認し、判断が確定するまで保留として追跡する。テストを通すことだけを目的に期待結果を書き換えない。

不具合には再現条件、影響範囲、重大度、対応状況、再試験結果を紐づける。修正後は該当ケースの再試験と、影響範囲に応じた回帰テストを行う。

### 10.4 品質ゲート

リリース判定に向けて、少なくとも次の条件を確認する。

1. 対象コミットに対する自動テストの実行結果が確認でき、必須ケースが合格している。
2. `flutter analyze`に未解決のerror・warningが残っていない。
3. 重要なライフサイクル・永続化・復帰シナリオが検証されている。
4. リリース対象端末での受入試験と、必要なOS通知試験が完了している。
5. リリースを妨げる重大な不具合が残存していない。
6. 未実施・保留項目と残存リスクが明示され、リリース可否の判断材料が揃っている。

性能・アクセシビリティ・画面品質などの定量的な受け入れ基準は、対象端末や実測結果を踏まえてテスト仕様書で具体化する。合否実績および最終的な品質評価は、本書ではなくテスト仕様書兼成績書に記録する。

### 10.5 計画の見直し

仕様変更、機能追加、不具合傾向、実施環境の変更に応じて、テスト範囲・優先順位・完了基準を見直す。公開版には品質保証の基本方針を残し、詳細なケース管理と実施状況は別文書で更新する。
